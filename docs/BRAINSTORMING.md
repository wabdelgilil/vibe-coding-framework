# وثيقة العصف الذهني المعتمدة: إطار عمل حوكمة التطوير بمساعدة الذكاء الاصطناعي

> **الحالة:** مرحلة العصف الذهني — جارٍ تنقيح الركائز (بانتظار إشارة البدء للتنفيذ)  
> **الاسم:** مؤجّل للاتفاق عليه لاحقاً  
> **الهدف:** بناء **مرجع شجري نقي من ملفات Markdown (`.md`) فقط** (بدون سكريبتات أو CLI أو اعتماديات) يعمل كـ "دستور وبنية معرفية" يقرأها الـ Agent مباشرة عند دخول أي مشروع جديد أو قائم، ليولّد منها تلقائياً ملف القواعد المخصص ونظام إدارة المشروع وبوابات الجودة والأمان الصارمة.

## 1. تشخيص المشاكل الجذرية في الـ Vibe Coding (Pain Points)

| المشكلة | المظهر العملي في المشروع | السبب الجذري |
| :--- | :--- | :--- |
| **المجاملة المفرطة والتطبيل (AI Sycophancy & Uncritical Agreement)** | المديح التلقائي لأي فكرة يطرحها المستخدم وتنفيذها كما هي حتى لو كانت تحمل كارثة معمارية أو أمنية أو ديوناً تقنية، بدلاً من تقديم رأي هندسي محايد وصريح. | تحيّز النماذج لإرضاء المستخدم عاطفياً وتجنب الاعتراض المهني. |
| **التنفيذ قبل التخطيط أو التخطيط المتعجل (Premature Execution & Rushed Planning)** | القفز مباشرة لكتابة الكود، أو كتابة خطة سطحية عامة (3–5 نقاط عائمة) دون قراءة الكود الحالي أو تحليل الأثر والحالات الحدية أو حسم الغموض، مما يؤدي لإعادة الشغل وكسر الأنظمة المترابطة. | اندفاع النموذج نحو "إظهار نتيجة سريعة" وغياب **بوابة جاهزية خطة صارمة** تمنع لمس الكود قبل تخطيط دقيق ومفصّل. |
| **الإصلاح قصير النظر "حلّها وخلاص" (Myopic Patch-to-Pass)** | التصرف لإسكات الخطأ أو تلبية الطلب الحالي بأي طريقة دون تقييم الأثر بعيد المدى (تراكم الديون، تشابك الطبقات، صعوبة التوسع لاحقاً) ودون التحقق من الالتزام بالقواعد البرمجية الصحيحة ودستور المشروع. | تحسين النموذج لـ "إنهاء التذكرة الحالية" بأقل مجهود دون تفكير معماري طويل المدى أو اختبار امتثال الحل للمعايير. |
| **انحياز الاختصارات والمسار السعيد (Shortcut Bias)** | كتابة كود يعمل ظاهرياً فقط، تجاهل الحالات الحدية، إخفاء الأخطاء (`catch {}` / `pass`)، أو قيم ثابتة (Hardcoded). | النماذج مُدرّبة على إنهاء المهمة بأسرع شكل ظاهري ممكن. |
| **بصمات الذكاء الاصطناعي في المخرجات (AI Footprint & Synthetic Artifacts)** | بقاء تعليقات آلية سطحية (`// loop over items`)، تواقيع أو `Co-Authored-By` للذكاء الاصطناعي في الـ Git، صياغات إنشائية متكررة في التوثيق والواجهات، أو بيانات وصفية افتراضية لمكتبات التوليد في الملفات والـ Manifests. | غياب معيار "صفر بصمة ذكاء اصطناعي" يفرض أن تبدو كل المخرجات (كود، التزامات Git، توثيق، ومستندات) كعمل مهندس خبير. |
| **غياب الكود النظيف (Poor Clean Code)** | تسميات غامضة، دوال طويلة ومتداخلة، منطق مكرر (Copy-Paste)، وغياب الانضباط البنيوي. | كتابة الكود بشكل ارتجالي سطراً بسطر دون معايير تصميم واضحة. |
| **ضعف قابلية التوسع (Lack of Scalability)** | تصميم يعمل لمستخدم واحد و10 سجلات فقط: استعلامات $N+1$، غياب الـ Pagination والفهرسة، حالة مخزنة في الذاكرة (In-Memory State)، وعمليات متزامنة تحجب التنفيذ. | التركيز على "إثبات الفكرة" دون التفكير في نمو البيانات أو عدد المستخدمين أو الأحمال. |
| **ضعف قابلية الصيانة (Poor Maintainability)** | ملفات ضخمة (God Files)، تشابك طبقة الواجهة مع المنطق وقاعدة البيانات، كود ميت، وتعديل ميزة يكسر ميزات أخرى. | غياب فصل المسؤوليات (SoC)، وضعف الاختبارات السلوكية، وتراكم الديون التقنية بصمت. |
| **غياب أو تقادم التوثيق المعياري (Missing / Stale Standard Docs)** | غياب الوثائق المعيارية للمشروع ولكل ميزة تُضاف أو تُعدّل (مثل `SRS`، مواصفات الميزة `Feature Spec`، تصميم النظام، عقود الـ API، `ADRs`، وسجل التغييرات `CHANGELOG`)، أو بقاء الوثائق قديمة لا تطابق الكود الفعلي. | التعامل مع التوثيق كخطوة شكلية ثانوية بدلاً من كونه جزءاً إلزامياً متزامناً مع إضافة أو تعديل أي ميزة. |
| **الارتجال من الذاكرة وتجاهل المهارات والبحث (Memory-Only Improvisation)** | الاعتماد على المعرفة العامة/القديمة فقط في مهام متخصصة (خاصة تصميم الواجهات UI/UX أو المكتبات الحديثة)، وتجاهل المهارات (Skills) المتوفرة أصلاً في المشروع أو عدم البحث للتحقق قبل التنفيذ. | استسهال الارتجال المباشر بدلاً من فحص المهارات والأدلة المتاحة أو التحقق من التوثيق الحديث وفق معيار مفاضلة واضح. |
| **الاعتماد الأعمى على السكربتات دون قراءة مباشرة (Blind Script Trust)** | تشغيل سكربت فحص أو مراجعة أو تعديل جماعي ثم إعلان "تم التحقق 100%" بناءً على ناتج السكربت فقط دون قراءة الكود الفعلي، مما يمرّر أخطاءً منطقية أو قصوراً في السكربت نفسه. | الاكتفاء بالفحص السطحي الآلي وتجاهل الفحص الدلالي (Semantic Verification) عبر قراءة الملفات مباشرة. |
| **ثغرات الأمان والترقيع الصامت** | أسرار مكشوفة، غياب التحقق من المدخلات، تعطيل قواعد الـ Linter/Types أو تعديل الاختبار لينجح عند الفشل. | التعامل مع "إزالة رسالة الخطأ" كهدف بدلاً من إصلاح الخلل الحقيقي. |
| **سوء تحديد الأولويات وتجاهل الاعتماديات (Faulty Prioritization & Dependency Blindness)** | تنفيذ المهام بالتسلسل النصي الأعمى (`1 ← 2 ← 3`) رغم أن المهمة (1) تعتمد على المهمة (4) أو تتعارض معها، أو تأجيل ثغرة أمنية/أساسية لصالح ميزة فرعية، مما يسبب إعادة شغل وتضارباً في الكود. | غياب تحليل الاعتماديات والتعارضات (Dependency Graph) وسلم أولويات واضح قبل البدء، وعدم الرجوع للمستخدم عند تساوي أو تعارض أولويات العمل. |
| **فوضى إدارة المشروع وتآكل السياق (Context Drift)** | نسيان القرارات السابقة، تداخل المهام، وترك ملفات مبعثرة في جذر المشروع بين جلسة وأخرى. | الاعتماد على ذاكرة المحادثة المؤقتة بدلاً من سياق مكتوب ومهيكل (Context-as-Code). |

## 2. القرارات التصميمية المحسومة (Locked-In Decisions)

1. **الشكل المعماري (Form Factor):** شجرة تفصيلية من ملفات `.md` فقط — **صفر سكريبتات، صفر CLI، صفر اعتماديات**.
2. **نقطة الدخول وآلية العمل (Direct Hub Execution):** ملف مركزي واحد (`INDEX.md`) يربط مجموعة من **الركائز (Pillars)**، وكل ركيزة تحتها شجرة ملفاتها التخصصية. يدخل الـ Agent مباشرة، يقرأ الملف المركزي كتعليمات تشغيلية، ويبني نظام القواعد وإدارة المشروع تلقائياً.
3. **اللغة (Language):** **الإنجليزية بالكامل** لجميع ملفات الشجرة والمخرجات.
4. **التوافق مع أدوات الذكاء الاصطناعي (Multi-Agent Output):** توليد مرن يكيّف ملف القواعد مع الأداة المستخدمة (`AGENTS.md`, `GEMINI.md`, `CLAUDE.md`, `.cursor/rules`, `.github/copilot-instructions.md`).
5. **مستوى الصرامة (Always Strict Quality + Proportional Ceremony):** صرامة هندسية كاملة وموحّدة دائماً على **جودة الكود والأمان ومنع الاختصارات والتحقق** دون أي تنازل، بينما يتناسب **عمق ملفات التخطيط والتوثيق** مع حجم التغيير الفعلي (إصلاح بسيط ← خطة من ملف واحد وتحديث المستند المتأثر فقط دون توليد ملفات فارغة؛ ميزة جديدة أو تعديل معماري ← الشجرة الكاملة والملفات المعيارية الكاملة).
6. **حيادية التقنية (100% Pure Language-Agnostic):** معايير عامة لأي لغة، وتلزم الـ Agent بتهيئة أدوات الفحص الحتمية القياسية للغة المشروع تلقائياً.
7. **نطاق المشاريع (Greenfield + Brownfield):** دعم المشاريع الجديدة من الصفر + إدخال الإطار على المشاريع القائمة بأمان.

### البنية الداخلية الموحّدة لكل ملف ركيزة (Standard Pillar Document Anatomy)
لكي تكون كل ملفات الشجرة متسقة وسهلة التنفيذ والتدقيق من قِبل أي Agent، يلتزم كل ملف معياري في الركائز ببنية ثابتة من 4 أقسام:
1. **Objective & Scope** (الهدف والنطاق بدقة).
2. **Mandatory Standards** (القواعد الإلزامية بلغة حازمة `MUST` / `MUST NOT`).
3. **Prohibited Anti-Patterns** (الأنماط والاختصارات الممنوعة مع أمثلة واضحة).
4. **Verification & Audit Checklist** (قائمة تحقق قابلة للفحص والإثبات قبل إغلاق أي مهمة أو عند تقييم النضج 1–5).

## 4. نموذج إدارة المشروع الشجري داخل أي مشروع مستهدف (Hierarchical Planning Model)

بدلاً من تكديس كل التفاصيل داخل `MASTER_PLAN.md` أو داخل ملف مهمة واحد ضخم، يُنظّم الإطار إدارة المشروع في المستودع المستهدف بالشكل التالي:

```text
project_management/
├── MASTER_PLAN.md                           # الواجهة الأولى فقط: قائمة المواضيع/الخطط النشطة + حالتها + رابط لمجلد كل خطة
├── COMPLETED_WORK.md                        # الفهرس التنفيذي للأعمال المكتملة والمؤرشفة
│
├── plans/                                   # مجلد الخطط النشطة — لكل موضوع/ميزة مجلد مستقل بشجرته الخاصة
│   ├── 01_small_task/                       # مثال لمهمة صغيرة: ملف واحد مركز يكفي
│   │   └── plan.md
│   │
│   └── 02_complex_feature/                  # مثال لميزة كبيرة/معقدة: شجرة ملفات حسب الحجم والتعقيد
│       ├── INDEX.md                         # مدخل خطة الميزة ونطاقها ومعايير القبول
│       ├── 01_spec_and_contracts.md         # المتطلبات التفصيلية، الحالات الحدية، والعقود
│       ├── 02_phases/                       # تقسيم التنفيذ إلى مراحل ذرية صغيرة
│       │   ├── phase_01_data_layer.md
│       │   ├── phase_02_core_logic.md
│       │   └── phase_03_integration.md
│       └── 03_verification.md               # بوابة التحقق، الاختبارات، والمراجعة الخصومية
│
└── archive/                                 # أرشيف مجلدات الخطط المكتملة بعد اجتياز بوابة التحقق
```

**الميزة الجوهرية لهذا النموذج:**
- يبقى `MASTER_PLAN.md` خفيفاً وسريع القراءة (واجهة أولى فقط دون تفاصيل تنفيذية مزدحمة).
- تتمدد شجرة كل خطة أو تنكمش تلقائياً حسب **حجم وتعقيد المهمة** دون إجبار المهام الكبيرة على ملف واحد متضخم، ولا إجبار المهام الصغيرة على ملفات زائدة.
- يقرأ الـ Agent فقط ملف المرحلة التي يعمل عليها حالياً، مما يمنع تشتت الانتباه وتآكل السياق.

> **الخطوة التالية (معلّقة بانتظار إشارتك):**  
> أخبرني إذا كانت هناك ركائز أو مشاكل أخرى تريد إضافتها في مرحلة العصف الذهني، أو متى أردت الانتقال للتنفيذ.
